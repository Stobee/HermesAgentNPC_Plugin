Hermes 서버 구현 준비물 체크리스트

UE5 플러그인과 통신할 Hermes 에이전트 서버를 만들기 전에 갖춰야 할 것들입니다. 위에서부터 순서대로 처리하면 됩니다 — 체크 상태는 브라우저에 저장됩니다.

서버 OS Windows 포트 8770/TCP 에이전트 Hermes (고정) LLM 백엔드 llama-server (고정)
0 / 0 
UE5 플러그인  ──소켓 프로토콜──▶  Hermes 에이전트  ──HTTP/SSE──▶  llama-server
  (게임마다 다름)     (공개 계약)        (이번 구현 대상)              (LLM 백엔드)
서버 OS는 프로토콜의 일부가 아닙니다 계약은 TCP 위의 길이 프리픽스 프레이밍뿐이라 어느 플랫폼에서 구현해도 동일하게 동작합니다. 이 문서는 Windows 기준으로, 플랫폼에 따라 달라지는 부분만 다룹니다.

1첨부할 문서

작업을 시작하는 세션에 이 두 문서를 반드시 함께 넣으세요. 없으면 나머지 준비가 다 소용없습니다.

  • 와이어 계약 전체. 프레이밍, 메시지 10종, 에러 코드 10종, 액션 카탈로그, 클라이언트 한계값까지 들어 있어 이 문서 하나로 프로토콜 계층을 완전히 구현할 수 있습니다. UE5 코드를 볼 필요가 없습니다.

  • docs/superpowers/specs/2026-07-28-hermes-settings-globalization-design.md — 서버 모듈 경계와 llama-server 연동 지침. 이미 내린 결정들이라, 안 읽으면 처음부터 다시 설계하게 됩니다. 두 문서가 충돌하면 프로토콜 문서가 이깁니다.

2설치

구현 언어와 런타임은 자유지만, 아래 셋은 무엇을 고르든 필요합니다.

  • openssl.exe와 Git Bash가 함께 설치됩니다. TLS 인증서의 SPKI 핀을 산출할 때 씁니다. OpenSSL을 따로 설치할 필요 없이 이것 하나면 됩니다.

  • 레퍼런스 테스트 클라이언트를 돌리는 데 씁니다. nc나 telnet으로는 대체할 수 없습니다 — 4바이트 바이너리 길이 프리픽스를 만들어내지 못하기 때문입니다.

  • GBNF 문법 / JSON 스키마 제약과 SSE 스트리밍을 지원하는 빌드여야 합니다. 이 두 기능이 프로토콜 요구사항과 직접 맞물립니다 — 없으면 액션 화이트리스트를 구조적으로 강제할 수도, chat_delta를 보낼 수도 없습니다.

  • 프로토콜 계층은 TCP 소켓과 JSON만, llama-server와는 HTTP로 붙으므로 Windows에서 돌아가는 것이면 무엇이든 됩니다. 다만 세 가지를 확인하세요:
    ① 바이트 단위 소켓 I/O (길이 프리픽스를 직접 다뤄야 함)
    ② TLS 서버 소켓 또는 리버스 프록시 조합
    ③ 오래 열린 소켓과 llama-server로의 HTTP/SSE를 동시에 다룰 동시성 모델

3사전 설정

설치는 아니지만 코드를 쓰기 전에 끝내두면 삽질이 줄어드는 것들입니다.

  • 접속이 안 될 때 1순위 원인입니다. 프로토콜을 의심하기 전에 여기부터 확인하세요. 

    New-NetFirewallRule -DisplayName "Hermes 8770" `
  -Direction Inbound -LocalPort 8770 -Protocol TCP -Action Allow

  • New-SelfSignedCertificate로 만들 수 있습니다. 클라이언트는 TLS 실패 시 평문으로 폴백하지 않으므로, TLS를 켜는 순간부터 인증서가 반드시 유효해야 합니다. 리버스 프록시(Caddy · nginx · IIS/ARR)에서 종단해도 되며, 그 경우 인증서와 핀은 프록시 쪽에 속합니다.

  • 자체 서명 인증서를 쓴다면 클라이언트가 핀을 걸 수 있도록 공개해야 합니다. 핀은 인증서가 아니라 공개키에 겁니다 — 같은 키로 갱신하면 기존 핀이 그대로 유효합니다.
    PowerShell 파이프로 옮기지 마세요. 파이프가 바이트가 아니라 텍스트를 나르기 때문에 DER이 해시 전에 깨집니다. 파일을 경유해야 합니다. 

    openssl x509 -in server.crt -pubkey -noout -out pub.pem
openssl pkey -pubin -in pub.pem -outform der -out pub.der
$sha = [Security.Cryptography.SHA256]::Create()
[Convert]::ToBase64String($sha.ComputeHash([IO.File]::ReadAllBytes("pub.der")))

  • 모델 로딩에 시간이 걸립니다. 준비 완료를 알리는 시점을 미리 눈으로 확인해두세요 — 이것이 server_busy 에러 코드를 언제 내보낼지의 기준이 됩니다.

  • 접속 주소는 클라이언트 설정이며 프로토콜의 일부가 아닙니다. UE5 프로젝트의 Config/DefaultGame.ini가 현재 Host=192.168.0.111로 되어 있으니, 다른 머신에서 돌리면 그 값을 바꾸거나 -HermesHost= 실행 인자로 덮으세요.
    UE5와 같은 PC에서 개발한다면 127.0.0.1이 가장 편합니다 — 방화벽·NAT 문제가 사라집니다.

4시작 전 최종 확인

여기까지 통과하면 코드를 쓰기 시작해도 됩니다.

  • UE5가 다른 PC에 있다면 반드시 먼저 확인하세요.

    Test-NetConnection <서버IP> -Port 8770

  • LLM을 붙이기 전에 와이어를 먼저 맞추세요. 프레이밍 → TLS → 연결 수명주기 → 신원 → 대화 턴 → 액션 → 에러 코드 순서입니다. 초반 단계는 고정 문자열을 되돌려주는 더미 응답으로 끝까지 검증할 수 있고, 그래야 나중에 문제가 생겼을 때 프로토콜 탓인지 추론 탓인지 갈립니다.

  • 클라이언트는 아직 스펙의 일부만 구현되어 있습니다. 호환성 문제가 아니라 아직 만들지 않은 기능이며, 플러그인 쪽 별도 작업으로 진행 중입니다. 따라서 서버 개발 중 검증은 레퍼런스 클라이언트와 스텁으로 하세요. 아래 "현재 클라이언트가 하지 않는 것" 표를 확인하세요.

✓재량과 고정

무엇을 정할 수 있고 무엇이 이미 정해졌는지 — 착각하면 되돌리기 비쌉니다.

재량 (직접 정함)고정 (바꾸지 말 것)
모델 파일, 샘플링 파라미터에이전트는 Hermes, 백엔드는 llama-server
시스템 프롬프트 설계소켓 프로토콜 전체 (첨부 스펙)
대화 히스토리 보관 정책, 컨텍스트 윈도 관리액션 카탈로그 4종, 에러 코드 10종
chat_id 발급 방식, 인증서 발급 정책단일 NPC, 턴 직렬화, 서버 발급 신원
서버 측 레이트 리밋 수치문법 제약 디코딩 — 수단은 재량, 존재는 필수

!현재 클라이언트가 하지 않는 것

서버를 완성해도 곧바로 붙지 않습니다. 엔드투엔드 테스트를 계획하기 전에 읽으세요.

아직 없는 동작서버 입장에서 뜻하는 것
protocol_version · session_token 전송현재는 클라이언트가 player_id를 스스로 만들어 보냅니다
chat_delta · action_event 수신해당 메시지 타입 자체가 없습니다
자체 ping 개시 · 침묵 연결 회수서버 ping에 pong은 회신합니다. 서버가 자체 liveness 검사를 돌려야 합니다
chat 응답 타임아웃턴을 조용히 버리면 영원히 "생각 중..."에 머뭅니다
종료성 에러 코드 구분session_taken_over를 받아도 무한 재연결합니다. 세션 탈취를 켜는 시점에 eviction war가 실제로 발생합니다
TLS 전송설정 키는 있으나 소비하는 구현이 없어 평문 TCP만 말합니다
세션 탈취는 클라이언트 대응과 시점을 맞춰야 합니다 서버가 session_taken_over를 보내기 시작하는데 클라이언트가 아직 재연결 루프를 멈추지 못하면, 두 게임 인스턴스가 서로를 영원히 걷어찹니다. 플러그인 쪽 대응 작업이 끝난 뒤에 켜세요.

?흔한 실패와 진짜 원인

증상만 보면 엉뚱한 곳을 파게 되는 것들입니다.

증상먼저 확인할 것
클라이언트가 아예 접속하지 못함방화벽 인바운드 규칙 → Test-NetConnection → 그 다음이 코드
접속은 되는데 바로 끊김identified에 session_token을 넣었는지. 빠지면 클라이언트가 인증 실패로 간주하고 끊습니다
답변 텍스트가 뒤섞여 보임두 턴의 chat_delta를 교차 전송했는지. 턴은 직렬로 처리해야 합니다
게임 프레임이 끊기거나 메모리가 늘어남델타를 토큰마다 보내고 있는지. 50ms 또는 토큰 몇 개 단위로 묶어야 합니다
NPC가 도착했다고 말하는데 실제로는 이동 중action_result에 완료를 담았는지. 접수는 action_result, 완료는 action_event입니다
NPC 대사에 마크다운이나 툴 흔적이 보임출력 정제는 서버 책임입니다. 클라이언트는 text를 그대로 대사창에 표시합니다
